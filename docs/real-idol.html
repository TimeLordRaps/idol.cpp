Real Idol decoders

Use a latent produced by the Idol pipeline to run its octree and Gaussian decoders on the central processing unit (CPU), then write the resulting Gaussian splats to a file.

This page describes the native decoder interface. The complete image-to-output path additionally uses the upstream image encoders and denoiser; see getting started.

Export and run

Build the project as described in getting started. The export script also requires Python, NumPy, PyTorch, safetensors, plyfile, the downloaded Idol decoder files, and a checkout of the Idol software development kit (SDK).

python tools/export_idol.py --weights WEIGHTS_DIR --sdk IDOL_SDK_DIR --out idol-export
idol_decode idol-export --check --threads 8
idol_decode idol-export --latent latent.f32 --out splats.ply --threads 8
idol_mesh splats.ply mesh.obj

The weights directory must contain config.json, decoder.safetensors, and decoder_gs.safetensors. The input latent is a raw file of 32-bit floating-point values, ordered by token and then conditioning channel. The tested model uses 16 channels per token. --check compares the exported reference case, while --latent decodes an existing latent. These are different operations.

The default output is 262,144 Gaussians at octree depth 8. Sampling uses the runtime's own random generator, so matching a seed does not imply matching draws from PyTorch. The point cloud file uses binary little-endian Polygon File Format (PLY), with the exported axes rotated from z-up to y-up.

Library interface

idol::Decoders loads an export directory. Its octree_logits and gaussian_features methods operate on supplied points and latents; sample_anchors samples points and decode combines sampling, the Gaussian decoder, and activation. The public declarations and dimensions are in include/idol/decoders.hpp. This interface begins with a latent, not an image.

Checking and measuring

The decoder test compares small randomly initialized SDK decoder instances against the runtime and inspects a generated point cloud. Passing that test does not establish trained-model quality. tools/quant_idol.py scores decoder outputs on supplied held-out latents, and tools/bench_idol.py times decoder operations. These measurements exclude latent generation. The benchmark's profile shares aggregate both decoders and warm-ups; they are not a breakdown of Gaussian decoder wall time.

The evaluation scripts cache cases, calibration statistics, and sensitivity results under their work directory. Those caches are not bound to all input files or settings. Use a new work directory when changing models, latents, calibration settings, or evaluation code; do not assume an existing cache matches a new run. Quantization refuses to overwrite an existing tier export. The mixed-plan search accepts --keep to retain scored exports; without it, its newly created temporary exports are removed after scoring.

A 32-object, 96-case matched-seed image-to-mesh and approximate-view evaluation is reported in the eight-bit fidelity study. Broader quantization sweeps and accuracy against ground-truth geometry remain unestablished. Measurements should identify the weights, inputs, arithmetic path, machine, and procedure.

Higher-accuracy quantization and construction checks

One approach leaves every octree tensor in 32-bit floating point and quantizes the Gaussian matrices. The tools/calibrate_gaussian.py script collects fresh Gaussian calibration matrices from a byte-disjoint holdout and calibration split, records input hashes, and checks available memory on Windows and Linux before each calibration case. tools/build_quant_candidate.py can then build an eight-bit candidate with those matrices, or use nearest-code rounding without calibration. Both tools require their destination to be new.

python tools/calibrate_gaussian.py --weights WEIGHTS_DIR --sdk SDK_DIR --latents LATENTS_DIR --out-dir CALIBRATION_DIR
python tools/build_quant_candidate.py --export FLOAT_EXPORT --hessians CALIBRATION_DIR/hessians.pt --out QUANT_EXPORT --report BUILD_REPORT.json --bits 8 --group 64 --method gptq

tools/gaussian_sensitivity.py optionally measures the effect of quantizing one Gaussian matrix at a time on calibration latents. Its report can be supplied to build_quant_candidate.py with --sensitivity-report and --keep-top-sensitive to leave selected matrices at full precision. The measurements are a heuristic: matrix effects can interact and the resulting model still needs held-out and construction evaluation.

The calibration output can be large. Its recorded input bytes do not establish the latents' origin, variety, or licensing. tools/audit_octree_preservation.py checks that the octree tensor bytes were retained, while tools/score_quant_candidate.py scores saved output cases. For downstream evidence, tools/eval_construction.py generates point clouds against a reference and a second reference seed; tools/compare_splats.py compares centers; tools/render_splats_preview.py creates approximate orthographic Gaussian previews; and tools/compare_meshes.py samples extracted mesh surfaces. Those Python comparison tools need NumPy, SciPy, plyfile, Pillow and, for meshes, trimesh. The previews are not the upstream renderer, and none of these comparisons supplies a ground-truth reconstruction.

See the exploratory benchmarks for the measured candidate tradeoffs and the limitations of the available cases.

Octree sampling comparison

idol_octree_compare REFERENCE_EXPORT CANDIDATE_EXPORT latent.f32 --anchors 8192 --level 8 --seed 0 samples both octrees on the same latent and, by default, the same seed. It bins the sampled anchors into leaf cells at the requested depth and reports half the sum of the absolute differences between their normalized cell counts. This empirical total variation is between zero and one: zero means identical sampled cell counts, and one means disjoint sampled cells. It is a comparison of finite sampled outcomes, not a distance between the exact probability distributions and not a visual-quality measure. Different paths may consume random numbers differently. The optional --candidate-seed lets you compare two seeds. Repeated --candidate EXPORT options reuse one reference sample for several candidates. --compare-levels 3,4,5,6,7,8 bins the same sampled anchors at several spatial scales, and --noise-seed 1 also compares the reference against itself with another seed; the latter is reported as candidate -1. These finite-sample comparisons must be interpreted alongside sampling variation.

The mixed-plan search accepts --octree-weight to place more emphasis on octree sensitivity in its allocation heuristic. It leaves the measured scores unchanged and can trade Gaussian accuracy for octree accuracy; evaluate both outputs and sampled cells rather than assuming an improvement.

For a fixed reference case, idol_decode --check also reports the mean and worst total variation between the reference and candidate eight-child probability vectors. This uses a stable softmax on each row of logits and is unchanged if a constant is added to all eight logits in a row. It measures probabilities at the supplied locations and level; saved anchor locations need not be parent-cell centers visited during sampling. It does not measure the entire sampled tree.
